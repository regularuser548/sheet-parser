# Google Sheets Importer

A Laravel application that reads multiple Google Sheets with similar-but-varied
structures and writes them into MySQL destination tables, driven by a
configurable mapping of spreadsheet sources, tabs, and columns. The destination
schema is altered automatically, and repeated daily runs are idempotent.

Administration is handled through an authenticated React/Inertia UI.

## Requirements

- A Linux (Ubuntu) host with Docker and Docker Compose (v2 plugin).
- [Laravel Sail](https://laravel.com/docs/sail) ships with the project, so no
  local PHP, MySQL, or Node installation is required.
- Composer and Node.js are only needed if you prefer to run the tooling on the
  host; everything can also be run inside Sail's containers.

### Installing Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker "$USER"
newgrp docker
docker compose version   # v2 plugin must be available
```

## Getting Started

The repository already contains the `docker-compose.yml` generated by Sail, so
you only need to prepare the environment file and install dependencies:

```bash
cp .env.example .env
composer install
./vendor/bin/sail key:generate
./vendor/bin/sail up -d
./vendor/bin/sail artisan migrate --seed
npm install
npm run build
```

The seeder creates an initial account:

- **Email:** `test@example.com`
- **Password:** `password`

### Starting and Stopping the Environment

```bash
./vendor/bin/sail up -d      # start in the background
./vendor/bin/sail down       # stop the containers
./vendor/bin/sail restart    # restart
./vendor/bin/sail tinker     # interactive shell
```

For day-to-day development (Vite, queue worker, scheduler, and logs in one
process) run:

```bash
composer run dev
```

which invokes `php artisan dev`.

## MySQL Configuration

The database runs in the `mysql` container and is only reachable on the Sail
network from the host.

```env
DB_CONNECTION=mysql
DB_HOST=mysql
DB_PORT=3306
DB_DATABASE=laravel
DB_USERNAME=sail
DB_PASSWORD=password
```

Useful commands:

```bash
./vendor/bin/sail artisan migrate
./vendor/bin/sail artisan migrate:fresh --seed
./vendor/bin/sail mysql                    # open a MySQL shell
./vendor/bin/sail artisan db:table sheet_sources   # inspect a table
```

`phpunit.xml` runs the test suite against a separate `testing` database, so
tests never touch your development data.

## Google Cloud Setup

The importer authenticates with a **Google service account** (not a personal
Google account).

### 1. Create a project

1. Open <https://console.cloud.google.com/> and create a project (for example
   `sheet-importer`).

### 2. Enable the Google Sheets API

1. Go to **APIs & Services → Library**.
2. Search for **Google Sheets API** and click **Enable**.

### 3. Create a service account and download credentials

1. Go to **APIs & Services → Credentials → Create Credentials → Service
   account**.
2. Give it a name (for example `sheet-importer`), grant no roles, and finish.
3. Open the newly created service account, go to **Keys → Add key → Create new
   key → JSON**, and download the key file.

Store the JSON key **outside source control**, inside the application (so the
container can read it):

```bash
mkdir -p storage/app/google
cp ~/Downloads/<service-account-key>.json storage/app/google/credentials.json
chmod 600 storage/app/google/credentials.json
```

### 4. Share each spreadsheet with the service account

A service account has no access to your files by default. Open each spreadsheet
you want to import, click **Share**, and invite the service account's email
(`<id>@<project>.iam.gserviceaccount.com`) as a **Viewer**.

Then point the environment variable at the key file:

```env
GOOGLE_SHEETS_CREDENTIALS=/var/www/html/storage/app/google/credentials.json
GOOGLE_SHEETS_TIMEOUT=30
GOOGLE_SHEETS_RETRIES=3
```

> The path must be readable **inside the container**, which is why the file is
> placed under `storage/app/`. A source may override this with its own
> `credentials_path` in the UI if you use more than one service account.

## Running Migrations and Seeders

```bash
./vendor/bin/sail artisan migrate
./vendor/bin/sail artisan migrate --seed
./vendor/bin/sail artisan migrate:fresh --seed   # rebuild from scratch
```

Application tables are managed by normal migrations. Destination tables for
imported data are created by the importer at runtime (see **Security
considerations**), never by migrations.

## Building the Administration UI

Sign up or sign in, then manage imports at **Sources** and **Import history**
in the sidebar.

The workflow is:

1. **Sources** (`/sheets/sources`) — create a spreadsheet source with its
   Google spreadsheet ID, optionally upload/point at credentials, and enable it.
2. **Edit a source** — add **tabs** (the worksheet names you want to import).
3. **Mappings** (per tab) — for each destination table, define source-to-
   destination column mappings with a data type, nullability, and optional
   default.
4. **Validate** the configuration (runs `sheets:validate` without writing data).
5. **Import** a single source manually from the source edit page, or let the
   scheduler run all enabled sources.

History, statuses, and per-run counts are shown on **Import history**
(`/sheets/runs`).

### Spreadsheet Format

- The **first row** of a tab is treated as column headers.
- Columns may appear in **any order**; headers are matched by name, not
  position.
- Source columns that are **not mapped are ignored**.
- A tab may map to **multiple destination tables** with different schemas.
- Headers are normalized (trimmed, case-insensitive) for matching.

### Mapping Example

| Source header | Destination column | Type      | Nullable | Notes                 |
| ------------- | ------------------ | --------- | -------- | --------------------- |
| `Name`        | `name`             | `string`  | yes      |                       |
| `Total $`     | `total`            | `decimal` | no       | `default_value` = `0` |
| `Is Paid`     | `is_paid`          | `boolean` | yes      |                       |
| `Order Date`  | `ordered_at`       | `date`    | yes      |                       |
| `Details`     | `meta`             | `json`    | yes      | stored as JSON text   |

Supported data types: `string`, `text`, `integer`, `bigInteger`, `float`,
`decimal`, `boolean`, `date`, `datetime`, `json`.

### Destination Schema

When an import runs, the importer:

- creates the destination table if it does not exist (with an auto-incrementing
  `id` primary key),
- adds any mapped columns that are missing, using the configured data type,
- logs every runtime schema change,
- rejects unsafe or protected identifiers (application tables such as `users`
  are never touched).

## Running Imports

```bash
./vendor/bin/sail artisan sheets:import                 # all enabled sources
./vendor/bin/sail artisan sheets:import <source>        # one source (ID or name)
./vendor/bin/sail artisan sheets:import --dry-run       # validate only
./vendor/bin/sail artisan sheets:validate               # configuration report
./vendor/bin/sail artisan sheets:validate --offline     # without reading sheets
./vendor/bin/sail artisan sheets:import --queue         # dispatch jobs
```

Sources are processed independently, so one failing spreadsheet does not stop
the others. Rows are deduplicated by a hash of the converted payload, so
re-running an import does not create duplicates; matching rows are updated
instead.

### Scheduler

`sheets:import` is scheduled daily at 02:00 (see `routes/console.php`) with
`withoutOverlapping`, `onOneServer`, and `runInBackground`. Start it with:

```bash
./vendor/bin/sail artisan schedule:work
```

or, in a deployment, the usual `* * * * * php /path/artisan schedule:run` cron
entry.

### Queue Worker

Large imports can run in the background:

```bash
./vendor/bin/sail artisan queue:work --tries=3
```

Jobs are dispatched with `sheets:import --queue` or the in-UI import action
when configured. `composer run dev` starts a worker for you in development.

## Viewing Logs and Failed Imports

```bash
./vendor/bin/sail artisan pail                    # tail the log live
./vendor/bin/sail artisan logs:failed             # failed jobs
cat storage/logs/laravel.log
```

Per-run status, row counts, and error details are recorded in the `import_runs`
table and shown on **Import history**. Failed configuration problems are
reported as validation issues rather than aborting the whole import.

## Ubuntu Setup Script

`setup.sh` is an idempotent helper for a fresh Ubuntu host. It:

- verifies (or installs) Docker and Docker Compose,
- copies `.env` from `.env.example` if missing (asking before overwriting),
- installs Composer dependencies and generates an app key if absent,
- installs/builds frontend assets,
- starts Sail and runs migrations with seeding,
- configures the scheduler via cron and documents the queue worker,
- prints the remaining Google credentials steps.

```bash
chmod +x setup.sh
./setup.sh
```

The script refuses to clobber an existing `.env` without confirmation and exits
with a clear message when a required tool is missing.

## Security Considerations

- **Keep credentials out of source control.** Never commit the service account
  JSON; it lives under `storage/app/` and is read via `GOOGLE_SHEETS_CREDENTIALS`.
- **Share spreadsheets explicitly** with the service-account email; give the
  minimum (Viewer) access.
- **Identifiers are validated**, not interpolated: destination table and column
  names are checked against safe identifier rules before any DDL runs, and
  application tables are protected (`DestinationSchemaManager::PROTECTED_TABLES`).
- **Runtime DDL is limited** to explicitly configured destination tables and
  mapped columns; the primary key column cannot be configured.
- **Authentication and email verification** protect every `/sheets/*` route.
